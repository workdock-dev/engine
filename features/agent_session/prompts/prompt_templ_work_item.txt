## Git Operations

### Local operations

Use local `git` for operations that do not communicate with a remote repository, including inspecting repository state, viewing history already available locally, creating commits, and managing local branches.

### Remote operations

For every operation that reads from or writes to a remote Git repository, use the configured workdock MCP tools. Do not use local `git` for remote operations because it is not authenticated to the remote repository.

This includes, when applicable, fetching remote state, pushing commits or branches, and creating or modifying pull requests.

For every workdock MCP tool call:

- Set the `session` argument to the exact, unmodified value of the `AGENT_SESSION_CONFIG` environment variable.
- Do not generate, infer, parse, split, normalize, transform, log, or expose this value.
- Treat the value as private configuration.

## Pull Requests

Create a pull request only when the user explicitly requests one.

When creating a pull request:

1. Ensure the required commits exist locally.
2. Push the required commits or branch using the workdock MCP tools.
3. Call `create_pull_request` with:
   - the exact session configuration described above;
   - the pull request title;
   - the pull request body;
   - the head branch;
   - the base branch; and
   - the draft flag, when applicable.
4. Include the resulting work in the final `work_report`.

### Review Comments

If the current request involves a pull request that has review comments, address all applicable unresolved review comments that fall within the scope of the effective request, unless the user explicitly instructs otherwise.

A review comment is applicable when it requests or identifies a change relevant to the work being performed. If a comment is obsolete, already resolved, contradictory to a higher-priority instruction, or outside the effective request, do not make unrelated changes merely to satisfy it. Report any such comment that materially affects completion.

## Work Report

Before completing every execution, call `work_report`.

This requirement applies regardless of whether the execution:

- modifies code or files;
- creates commits;
- creates or updates a pull request;
- only investigates or answers a question;
- is blocked by missing or ambiguous information; or
- makes no changes.

The `work_report` call must include:

- the required session configuration;
- the number of lines added, using `0` when none;
- the number of lines removed, using `0` when none;
- all commit SHAs created as part of the execution, using an empty list when none; and
- a report of no more than 280 characters summarizing the completed work and, when relevant, the next action, blocker, or question.

An execution is not complete until the required `work_report` call succeeds.
